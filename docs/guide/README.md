# Kubernetes Lab: Two Varnish, Measured

**You build a small cluster by typing the lab's files yourself, put two Varnish caches on it, and measure what a second Varnish really costs in cold pages, and what routing by URL buys back.** You end with the same files this repository holds, and numbers of your own.

This is test and research on a laptop cluster. The origin is an invented web app that takes 300 ms per page, and the load is invented too. Nothing here is production-like, and nothing in it is built or hardened for production.

**You type every file but two.** The two ConfigMap files of Parts 1 and 2 are generated by `kubectl`, because code inside YAML is an indentation trap; Part 2 and the tightening section replace them. After each part you commit, so your folder keeps a record of what you built and when it changed.

If you'd rather run the finished lab than build it, [the quick path](../from-nothing.md) goes from an empty laptop to both hit rates in six steps. The load runs measured on the published files are in [results.md](../../results.md); the memory readings in Part 2 and the tightening section come from this guide's own sample runs.

The sample output on every page comes from runs made while this guide was written. Its pod names, hashes, addresses, times and numbers may differ on your machine.

## The road

| Part | You build | The Kubernetes ideas |
|---|---|---|
| [**1. A cluster and a slow origin**](1-a-cluster-and-a-slow-origin.md) | A three-node cluster and a small backend that takes 300 ms per page | Node, namespace, ConfigMap, Deployment, Service, probes, requests and limits, stopping when asked, draining a node |
| [**2. One Varnish in front**](2-one-varnish-in-front.md) | Varnish caching the origin, with its VCL kept in the repository | Kustomize, rolling a config change, reading `varnishstat` inside a pod, a load Job |
| [**3. Two Varnish, and the problem**](3-two-varnish-and-the-problem.md) | A second Varnish, then a router that sends each URL to the same one | How a Service spreads requests, StatefulSet, headless Service, routing by URL with consistent hashing, reading what a router believes |
| [**Between 3 and 4. Tighten what you typed**](3b-tighten-what-you-typed.md) | The same lab with nothing left to a default, rebuilt from its folder | Probe timeouts, a namespace owned by the folder, what a cache pod's memory is made of, `emptyDir`, a drain that refuses, pinning the cluster's version |
| [**4. Kill one under load**](4-kill-one-under-load.md) | The failure test, with the numbers written down | A timeline in the load, what a router does with a lost backend, spreading pods across nodes, PodDisruptionBudget, drain against delete, letting a pod finish before it stops |

**The three numbers the lab exists to produce:**

1. The cache hit rate with two Varnish and requests spread evenly.
2. The hit rate with each URL always sent to the same Varnish.
3. After one Varnish is killed under load: the share of pages that go cold, and how long it takes to warm back.

## Before you start

You need Docker running, `kind`, `kubectl`, `python3`, `curl` and `ruff`, the Python linter. Check them:

```bash
kind version
```

```bash
kubectl version --client
```

```bash
python3 --version
```

```bash
curl --version
```

```bash
ruff --version
```

**You should see:** a version line from each. This guide was run with kind 0.32 and kubectl 1.36, and the cluster it builds runs Kubernetes 1.36.1.

Build your lab in a new, empty folder, not inside a clone of this repository. The repository already holds the finished files, so at the end you can compare yours with them line by line.
